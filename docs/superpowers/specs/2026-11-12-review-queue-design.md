# Очередь ревью: дизайн

Дата: 2026-11-12. Расширение: GitHub PR Watcher (Chrome MV3, ванильный JS, без сборки, тесты на `node --test`).

## Зачем

Сейчас расширение следит только за *моими* PR. Нужен второй инструмент: всегда актуальная очередь PR, где ждут *моего* ревью, чтобы за секунду понять, какой PR сейчас нуждается в ревью больше всего, сколько там работы и что по нему уже сделали другие.

Главное здесь очередь, а не уведомления. Уведомления есть, но выключены по умолчанию.

## Цели

1. Список открытых PR в выбранных репозиториях, где запрошено моё ревью, отсортированный по умолчанию по принципу «нужнее всего сейчас».
2. В каждой строке без открытия PR видно:
   - сколько работы (размер);
   - сколько PR ждёт;
   - первичное это ревью или ре-ревью;
   - апрувы и запросы изменений от других;
   - треды: решено / не решено, а среди нерешённых — с ответом автора / без ответа.
3. Другие сортировки и фильтр «первичные / ре-ревью».
4. Можно скрыть зависший PR, вернуть его и посмотреть список скрытых.
5. Можно одной кнопкой открыть новую сессию Claude Code в Claude Desktop с промптом из настроек и ссылкой на PR. Это работает и для чужих PR (промпт для ревью), и для своих (отдельный промпт, например «разбери комментарии ревьюеров»).
6. Есть два уведомления, отдельно о первичном запросе и о ре-ревью, оба по умолчанию выключены.

## Не-цели

- Делать ревью внутри расширения: оставлять комментарии, апрувить.
- Менять существующую вкладку «Мои PR», кроме кнопки «Открыть в Claude».
- Читать правила branch protection (сколько апрувов нужно). Достаточно ли апрувов, определяется по `reviewDecision === "APPROVED"`.

## Анти-цели (провал, даже если всё «работает»)

- Сортировка «нужнее всего» ставит наверх непонятно что, и пользователь перестаёт ей доверять. Поэтому у каждой строки есть видимая причина её места.
- Строки перегружены нулевыми и бессмысленными бейджами. Нулевые значения не показываются.
- Popup заметно медленнее открывается, или опрос съедает лимит GitHub API.

## UX

### Popup

- **Вкладки.** Вверху две вкладки: «Мои PR» и «На ревью N», где N — число PR в активной очереди без скрытых и без «Ждут автора». Последняя открытая вкладка запоминается в `localStorage` (как свёрнутые репозитории сейчас). Шапка с кнопками «обновить» и «настройки» общая для обеих вкладок. Кнопка «отметить всё прочитанным» видна только на «Мои PR».
- **Панель управления под вкладками:**
  - Слева фильтр-чипы со счётчиками: «Все N · Первичные N · Ре-ревью N».
  - Справа выбор сортировки: «Нужнее всего» (по умолчанию), «Дольше всех ждут», «Новые», «Никто не ревьюил», «Маленькие сначала».
  - Выбранные фильтр и сортировка запоминаются в `localStorage`.
- **Список один, общий для всех репозиториев, без группировки.** Название репозитория стоит в мета-строке.
- **Строка PR:**
  1. Заголовок (до двух строк), справа бейдж размера.
  2. Мета-строка: `repo #number · автор · ждёт N`. Время ожидания окрашивается по возрасту: обычный цвет, затем жёлтый с 2 дней, затем красный с 5 дней.
  3. Бейджи. Показываются только ненулевые, в таком порядке:
     - «ре-ревью» или «никто не смотрел»;
     - ✓N — апрувы других, с логинами в подсказке;
     - ✗N — запросы изменений, с логинами в подсказке;
     - треды «решено/всего»;
     - «N без ответа» — нерешённые треды, где последний комментарий не от автора PR;
     - «N с ответом» — нерешённые треды, где последним ответил автор PR;
     - точка CI (жёлтая или красная; зелёная только если её не жалко по месту — на усмотрение билдера).
  4. Серая строка-причина, например «↑ ре-ревью · ждёт 4 д · маленький» или «↓ уже хватает апрувов». Показывается только при сортировке «нужнее всего».
- **Действия в строке.** При наведении или фокусе справа появляются иконки «Открыть в Claude» и «Скрыть». Клик по строке, средний клик и Ctrl+клик работают так же, как на вкладке «Мои PR».
- **Скрытие.** После «Скрыть» строка сразу исчезает, внизу popup примерно 5 секунд показывается «Скрыто · Отменить».
- **Свёрнутые секции внизу списка:**
  - «Ждут автора · N»: PR, где я уже ревьюил и где сейчас не запрошено моё ревью. Если после моего последнего ревью есть новые коммиты, у такого PR бейдж «новые коммиты».
  - «Скрытые · N»: компактные строки с кнопкой «Вернуть».
  - Секции запоминают, свёрнуты они или нет.
- **Пустые состояния:**
  - «Нет PR, где ждут вашего ревью» — если репозитории выбраны, но очередь пуста.
  - «Выберите репозитории для ревью в настройках» с кнопкой — если список репозиториев для ревью пуст.
- **Черновики** в очереди не показываются.

### Размер PR

По сумме `additions + deletions`: XS ≤ 10, S ≤ 100, M ≤ 400, L ≤ 1000, XL > 1000. В подсказке «+A −D, N файлов». Пороги фиксированные (решение билдера-дизайнера, см. «Решения, принятые мной»). Цвета: XS и S — зелёный, M — серый, L — жёлтый, XL — красный.

### Ранжирование «нужнее всего»

Это моё предложение, пользователь его явно не подтверждал. Формулу нужно держать в одной чистой функции с тестами, чтобы веса было легко править.

- **Основа:** часы ожидания.
  - Первичное ревью: от последнего `ReviewRequestedEvent`, адресованного мне (или моей команде, если включено).
  - Ре-ревью: от более раннего из двух моментов — повторного запроса или первого коммита после моего последнего ревью.
- **Повышают:**
  - ре-ревью (автор ждёт именно меня);
  - никто, кроме автора и ботов, ещё не оставил ревью;
  - маленький размер (XS и S).
- **Понижают:**
  - `reviewDecision === "APPROVED"` (апрувов уже хватает);
  - есть активный запрос изменений, и после него не было коммитов (ход за автором).
- Каждый применённый фактор даёт фрагмент строки-причины. Показываются максимум три самых весомых.

**Как это сочетается: два яруса плюс поправки** (моё решение).

- **Ярус 1 — «ход за мной».** Все PR, кроме перечисленных ниже.
- **Ярус 2 — «ход не за мной».** Сюда попадают:
  - PR, где `reviewDecision === "APPROVED"`;
  - PR, где есть активный запрос изменений от другого ревьюера и после него не было коммитов.
- Любой PR яруса 1 стоит выше любого PR яруса 2, как бы долго тот ни ждал. Это сделано для доверия: наверху всегда то, что действительно ждёт меня.
- **Поправки** внутри яруса считаются в «эквивалентных часах ожидания»: score = часы ожидания + бонусы. Стартовые значения:

  | Фактор | Поправка |
  |---|---|
  | ре-ревью | +24 ч |
  | никто не ревьюил | +12 ч |
  | размер XS/S | +8 ч |

  Веса — константы в одном месте.
- **Строка-причина** показывает принадлежность к ярусу 2 (если PR там), затем поправки по убыванию, всего не больше трёх фрагментов.
- **Если нет `ReviewRequestedEvent`** (например, событие старше последних 20 в `timelineItems`), ожидание считается от `createdAt` PR.

Остальные сортировки:

- **Дольше всех ждут** — по времени ожидания по убыванию.
- **Новые** — по времени запроса, свежие сверху.
- **Никто не ревьюил** — сначала PR без ревью других, внутри по ожиданию.
- **Маленькие сначала** — по `additions + deletions` по возрастанию.

### Настройки

Новая секция «На ревью» на странице настроек:

1. **Репозитории для ревью.** Отдельный список с тем же поиском и выбором, что для своих PR, включая `owner/*`. Компонент выбора нужно переиспользовать, а не копировать: сейчас он завязан на глобальный `picker` в `options.js` и фиксированные id, его надо параметризовать.
   - Подсказки для этого списка: репозитории, где мне запрашивали ревью или где я ревьюил (`review-requested:@me`, `reviewed-by:@me`), а также владельцы из моих PR.
2. **Учитывать запросы на мои команды** — флажок, по умолчанию выключен. Выключен: в поиске `user-review-requested:<login>`. Включён: `review-requested:<login>`, который включает команды.
3. **Уведомлять:** «о новом запросе ревью» и «о запросе ре-ревью», оба по умолчанию выключены.
4. **Скрытые PR.** Список с «Вернуть» у каждого и «Вернуть все». Если скрытых нет, секция не показывается.

Новая секция «Открыть в Claude»:

1. **Промпт для ревью чужого PR.** Многострочное поле. По умолчанию: `Сделай ревью pull request {url}`.
2. **Промпт для своего PR.** По умолчанию: `Разбери комментарии ревьюеров в моём pull request {url} и предложи, что исправить`.
3. **Подстановки:** `{url}`, `{title}`, `{repo}`, `{number}`, `{author}`. Под полями подсказка со списком подстановок.
4. **Папки репозиториев** (необязательно). Пары «репозиторий → абсолютный путь», репозитории из обоих списков. Если путь задан, ссылка получает `folder=<путь>`, и Claude Desktop перед открытием попросит подтвердить папку. Если не задан, параметр `folder` не передаётся.

### Открыть в Claude

- Ссылка: `claude://code/new?q=<encodeURIComponent(промпт)>[&folder=<encodeURIComponent(путь)>]`. Источник: [Open Claude Desktop with a link](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link). Промпт только вставляется в поле ввода, не отправляется. Длина `q` ограничена примерно 14 000 символами; при превышении промпт нужно обрезать.
- **Без `folder`.** Документация не говорит, какая папка будет выбрана. Билдер должен проверить вручную, что происходит (скорее всего папка по умолчанию или последняя), и описать это в подсказке в настройках.
- **Как открыть `claude://` из расширения**, не оставив пустую вкладку, — на усмотрение билдера. Варианты: `chrome.tabs.update` текущей вкладки, временная вкладка с последующим закрытием и т. п. Chrome при первом открытии спросит «Открыть Claude?». В подсказке настроек упомянуть «Всегда разрешать».
- **Кнопка есть на обеих вкладках:** на «На ревью» с промптом ревью, на «Мои PR» с промптом своего PR.

### Уведомления

- **Новый запрос.** PR впервые появился в очереди как первичный. Первый опрос после включения функции или после смены репозиториев запоминает текущее состояние молча, как сейчас делает `diffPullRequests`.
- **Ре-ревью.** Появился новый `ReviewRequestedEvent` мне на PR, который я уже ревьюил.
- Клик по уведомлению открывает PR, как сейчас.

### Иконка расширения (бейдж)

Без изменений: считает только непрочитанное в моих PR. Очередь ревью видна на вкладке. Это моё решение, см. ниже.

## Данные

- **Поиск.** Тот же подход, что в `fetchPullRequests`: GraphQL `search`, разбиение по 256-символьному лимиту (`buildSearchQueries` нужно обобщить на произвольный префикс). Один запрос за опрос на обе вкладки, если укладываемся в стоимость; иначе два, на усмотрение билдера.
  - Активная очередь: `is:pr is:open archived:false draft:false user-review-requested:<login>` (или `review-requested:` с командами) + `repo:`/`user:`.
  - «Ждут автора»: `is:pr is:open archived:false reviewed-by:<login> -author:<login>` + репозитории, минус те, что уже в активной очереди.
- **Поля PR**, нужные сверх существующих: `author { login }`, `createdAt`, `additions`, `deletions`, `changedFiles`, `reviewDecision`.
  - `reviewRequests(first: 20) { nodes { requestedReviewer { ... on User { login } ... on Team { slug } } } }` — понять, запрошен ли я сейчас.
  - `timelineItems(last: 20, itemTypes: [REVIEW_REQUESTED_EVENT]) { nodes { ... on ReviewRequestedEvent { createdAt requestedReviewer { ... on User { login } ... on Team { slug } } } } }` — время запроса.
  - `reviews(last: 50) { nodes { state submittedAt author { login __typename } commit { oid } } }` — мои прошлые ревью, апрувы и запросы изменений других.
  - `commits(last: 1)` с `committedDate` и CI; для «первого коммита после моего ревью» достаточно `commits(last: 20) { nodes { commit { committedDate } } }`.
  - `reviewThreads(first: 50) { nodes { isResolved comments(last: 1) { nodes { author { login } } } } }` — для решённых, нерешённых и «последний ответ за автором».
  - Для своих команд, если флажок включён: `viewer { organizations(first: 50) { nodes { teams(first: 100, userLogins: [<login>]) { nodes { slug } } } } }`. Либо не определять адресата и считать, что запрос на команду — запрос мне. Решает билдер.
- **Хранение.** Отдельный ключ `chrome.storage.local`, например `reviewState`: снимок очереди, последняя проверка и база для уведомлений. Плюс `reviewIgnored: { [prKey]: { ignoredAt, title, url } }`. Скрытые хранятся отдельно от состояния, чтобы сброс состояния при смене токена их не стирал; при смене токена их стоит тоже очистить.
- **Авто-возврат из скрытых.** Если у скрытого PR появился `ReviewRequestedEvent` мне позже `ignoredAt`, PR удаляется из скрытых. Новые коммиты PR из скрытых не возвращают (одобрено пользователем). Закрытые и смёрженные PR удаляются из скрытых при опросе: их просто нет в результатах поиска.
- **Что значит «я ревьюил этот PR»** (моё решение). Это мой review в состоянии:
  - `APPROVED`;
  - `CHANGES_REQUESTED`;
  - `COMMENTED`, если у него непустое тело или хотя бы один комментарий, который не ответ в чужом треде (`replyTo == null`).

  Одиночный ответ в чужом треде ревью не считается. Поиск `reviewed-by:` поэтому даёт кандидатов, а окончательно фильтровать нужно после загрузки.
- **«Ждут автора»** (моё решение). Сюда попадают PR, где я ревьюил по определению выше и моё последнее значимое ревью не `APPROVED`. PR, которые я уже апрувнул, не показываются нигде: с моей стороны работа сделана.
- **Опрос очереди ревью** не зависит от списка репозиториев «Мои PR». Если пуст только один из двух списков, второй всё равно опрашивается. Ошибка «добавьте репозитории» показывается только на той вкладке, где список пуст.
- **Лимит API.** У GitHub 5000 пунктов в час. Ориентир — опрос обеих вкладок суммарно не больше примерно 1500 пунктов в час при интервале 2 минуты, то есть около 50 пунктов за опрос. Это бюджет, а не догма. Предпочтительный способ в него уложиться: дешёвый список (id, `updatedAt`, `reviewRequests`), затем подробности только для PR, у которых изменился `updatedAt` или которых ещё нет в кэше. Кэш подробностей лежит в `reviewState`. Если выяснится, что решение треда не меняет `updatedAt`, подробности нужно также перезапрашивать не реже раза в 10 минут. Снижать `first` у `reviewThreads` ниже 50 не нужно: бейдж «решено/всего» должен быть точным.

## Решения, принятые мной (пользователь может оспорить)

1. Формула «нужнее всего» и её веса (выше).
2. «Без ответа» означает нерешённый тред, где последний комментарий не от автора PR.
3. Пороги размера фиксированные, без настройки (в первом макете они были показаны как настраиваемые).
4. Бейдж иконки не учитывает очередь ревью.
5. Черновики скрыты всегда, без настройки.
6. Запросы на команды по умолчанию не учитываются.
7. «Ждут автора» — свёрнутая секция внизу, а не отдельный фильтр.
8. Плоский список без группировки по репозиториям, без переключателя группировки.
9. «Нужнее всего» состоит из двух ярусов («ход за мной» всегда выше «ход не за мной»), внутри яруса — часы ожидания с поправками в часах.
10. Ответ в чужом треде не считается моим ревью.
11. PR, которые я апрувнул, не показываются ни в очереди, ни в «Ждут автора».
12. Бюджет API — около 1500 пунктов в час, с кэшем подробностей по `updatedAt`.

## Оставлено билдеру

- Точная вёрстка в рамках существующих `theme.css`/`popup.css` (ширина popup 400px, светлая и тёмная темы).
- Способ открытия `claude://` без пустой вкладки.
- Один или два GraphQL-запроса за опрос.
- Определение моих команд или упрощение.
- Модульная структура: например `lib/review.js` для нормализации и ранжирования, `lib/claude.js` для построения ссылки. Чистые функции покрыть тестами в стиле существующих `test/*.test.js`.
